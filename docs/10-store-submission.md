## 2. iOS

### 2.1 Privacy Manifest (`PrivacyInfo.xcprivacy`)

Generated by Expo at prebuild and checked on 2026-10-01: `NSPrivacyTracking: false`,
`NSPrivacyCollectedDataTypes: []`, and required-reason APIs UserDefaults `CA92.1`, FileTimestamp
`C617.1`, SystemBootTime `35F9.1`. Those are the reasons React Native and AsyncStorage need.
If a later dependency adds a required-reason API, Apple's upload check emails the missing
category; add it under `ios.privacyManifests` in `app.config.ts`. No tracking domains. **VERIFY**
on the first App Store Connect upload (the check runs there, not locally).

### 2.2 Export compliance

`ios.config.usesNonExemptEncryption: false` is now set in `app.config.ts` (HTTPS only), so
App Store Connect will not ask on every upload.

### 2.3 App Privacy labels ("nutrition labels")

**DECISION.** Recommended answer: **Data Not Collected**, and tracking: **No**.

Reasoning: Apple counts data as "collected" when it is transmitted off the device in a way that lets
you or a third party keep it longer than needed to serve the request in real time. A barcode
lookup is a request answered in real time, and we operate no server. But Open Food Facts is a
third party that receives the barcode and an IP address, and the policy already says so. The
conservative alternative is to declare **Other Data / Product Interaction**, "not linked to the
user", "not used for tracking", purpose "App Functionality". If in doubt, choose the conservative
label: over-disclosing is never rejected, under-disclosing can be.

### 2.4 Purpose strings (already in the build)

- Camera: "CanMy*EatThis uses your camera to scan product barcodes." (build without photo ID)
- Photo library: "CanMy*EatThis only uses your photo library if you choose to add a photo." —
  **DECISION:** this build has no photo picking at all. An unused photo-library purpose string
  invites a reviewer question ("where do you use it?"). `expo-image-picker` is still linked.
  Either keep the string (harmless, matches the code that exists) or drop the plugin for the first
  release. Recommended: keep, and say so in the review notes.

### 2.4.1 First EAS iOS production build (2026-10-05) — checked, one fix

Build 1 (`0.0.1`): bundle id `app.canmyeatthis.mobile`, iPhone only, minimum iOS 16.4,
`ITSAppUsesNonExemptEncryption=false`, scene manifest with `EXExpoAppSceneDelegate` (D32 shipped),

**VERIFY** the sample barcode against Open Food Facts before submitting, and that the emergency

### 2.5.1 Medical-info guideline (1.4.1)

Apple scrutinises apps that give medical information. Our mitigations to cite if asked: sources
displayed above the fold, "not a vet, not a diagnosis" on first run and every result, every serious
answer routes to a vet or poison line, no dosing, no weight input. This is **pet** health, not
human health, which is lower risk but not exempt.

## 3. Android (Google Play)

### 3.1 Permissions in the release manifest

Verified 2026-10-04 on the first EAS production AAB (build 1, `0.0.1`): `CAMERA`, `INTERNET`,
`VIBRATE`, `ACCESS_NETWORK_STATE` (added by a dependency). Absent: storage, media, `RECORD_AUDIO`,
`SYSTEM_ALERT_WINDOW`.

### 3.2 Data safety form

**DECISION.** Recommended: **No data collected, no data shared**, "data is encrypted in transit"
(HTTPS), "users can request deletion": not applicable (no accounts). Google's definition of
"collect" excludes data processed ephemerally; the same barcode/IP reasoning as §2.3 applies. The
conservative alternative is to declare *Device or other IDs → IP address* and *App activity*,
shared with a third party (Open Food Facts), purpose "App functionality", optional.

### 3.3 Other declarations

- **Health apps declaration:** Play asks every app on the Console's list whether it is a health
  app. This app is **not** a human health or medical app (it covers pet toxicity). Answer
  "my app is not a health app", unless the questionnaire's wording for "provides health
  information" catches it. **VERIFY** the current wording in the Console.
- **Target audience:** 18+ (a safety-information app addressed to pet owners, not directed at
  children). Not a "Families" app.
- **Content rating:** IARC questionnaire: no violence, no user-generated content, no
  interaction. Expect "Everyone".
- **Ads:** none. **Financial / news / government:** none.
- **AI-generated content:** not applicable in the first release (no model). For the photo release,
  answer yes and rely on the in-app "Report a wrong answer" flow (already built).
- **Target API level:** whatever Expo SDK 57 / EAS targets (Play requires the latest within a
  year). **VERIFY** at upload.

## 4. Gates that block submission

1. **Hotlines verified by a person.** Release builds hide any hotline with `verifiedAt: null`
   (`hotlinesForRegion`, D30), and **all four registry entries are unverified today**: INTCF
   (ES, +34 915 620 420), Animal PoisonLine (GB, +44 1202 509 000), ASPCA APCC (US, +1 888 426
   4435) and Pet Poison Helpline (US, +1 855 764 7661). A release built now would show the
   emergency screen with **no numbers**, which is worse than not having it. Dial each, confirm it
   reaches the named service and takes pet cases, and record `verifiedAt` and the operating
   language(s): use `docs/eval/hotline-verification.md`. MX and AR have no entries on purpose
   (the registry comment says why), and the emergency screen already handles that: the user's own
   vet, "no line for your region", and the emergency-vet search. Until a number is verified, every
   region degrades to that same screen, which is acceptable but weak. **DECISION:** ship with only
   the lines you have verified, or hold the release until the US/ES/GB ones are.
2. **KB editorial gate** (§6 of `docs/07`): the two-independent-source check is a manual pass.
   Known exceptions: `pineapple` (D35). Also `lemon` cites ASPCA, which is not one of the source
   classes `docs/04` §2 names.
3. **Spanish walk-through** by a native speaker, including an emergency result and the store listing.
4. **Closed test** on Play (§1), and a TestFlight round with people outside the project.
5. **The first EAS production build must succeed** (see §6).

## 6. Pipelines and rollback

- `eas build --profile production --platform all`, then `eas submit --platform ios|android`.
  `eas.json` has an empty `submit.production`; it needs the App Store Connect app id and a Play
  service-account key (kept out of the repo: AGENTS.md #6; use EAS secrets).
- **Resolved 2026-10-04:** the first EAS production build failed with `Cannot find module
  'babel-preset-expo'` (a pnpm strict-layout problem: `babel.config.js` used a package the app
  never declared). Declared it in `apps/mobile/package.json` (`568c168`); the second build
  (`518324fd`) finished. A local `gradlew` release build still fails on a different Babel
  resolution error because the local pnpm store holds stale duplicate versions; EAS installs from
  the lockfile and is the build that matters. Project: `@jasalguero1/canmyeatthis`; the Android
  keystore is held by EAS. iOS: build 1 finished 2026-10-05 (see §2.4.1); rebuild after the microphone fix.
- **Rollback plan.** Stores cannot un-ship. (1) Halt a staged rollout (Play: halt; App Store:
  phased release can be paused). (2) Ship a fixed build; because the KB is bundled (D21), a
  corrected verdict **is** an app update, so expedite review for a wrong *toxic/no known toxicity*
  answer. (3) For a wrong verdict, the fastest mitigation is deleting the entry (omission renders
  `unknown`) and releasing. (4) OTA KB updates are deliberately out of scope until after the first
  release (`docs/07`); revisit if (3) proves too slow. **Time it once** (acceptance item).
- Keep: the `review` block per KB entry (audit trail), and `docs/eval/`.

## 7. Performance pass (needs a mid-range Android phone)

Cold start < 2 s, resolution < 50 ms, 12 MP processing (not used in this release), memory and
bundle size. The release JS bundle is **4.8 MB** (Hermes bytecode, Android, 2026-10-01); each KB
language artefact is ~125 KB raw. Emulator timings are not evidence for the budgets.
